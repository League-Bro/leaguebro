# League Bro: notes for Claude

An ad-free, lightweight League of Legends companion for Windows (a personal alternative to Blitz). Dom (GitHub `doliaro`) owns it and shares it with a few friends through GitHub Releases. Repo: https://github.com/doliaro/leaguebro (renamed from `leaguebuddy` in October 2026; the app was renamed from League Buddy to League Bro in issue 5). Dom's local folder is still `Desktop\leaguebuddy`: a fresh clone elsewhere hit Windows Smart App Control blocking Cargo's build scripts, so he kept the old folder. The updater endpoint uses the new URL; copies installed before the rename still have the old one and rely on GitHub's redirect, so never create a new `doliaro/leaguebuddy` repo.

Stack: **Tauri 2** (Rust backend, `src-tauri/`) + **Angular 21** (standalone components, signals, zoneless, `src/`). Windows and macOS. macOS-only bits: `tauri.macos.conf.json` (`.app`/`.dmg`, ad-hoc signing), the lockfile path inside `/Applications/League of Legends.app/Contents/LoL` (`lcu.rs`), `open` for links (`lib.rs`), the overlay joining every Space (`lib.rs` setup) and Cmd+1…5 tabs (`core/platform.ts`). Nobody on the team has a Mac, so Mac builds only come from the release workflow.

## Commands

```powershell
scripts\setup-dev.cmd        # one-time dev environment setup (winget installs; -Build to precompile Rust)
npm run tauri dev            # run the app (UI hot-reloads; Rust changes rebuild + restart)
npm start                    # UI only in a browser at http://127.0.0.1:4200 with demo data
                             #   ?scene=champselect  -> champ select demo
                             #   ?scene=postgame     -> post-game summary demo
                             #   ?scene=postgame-bad -> a bad game, with the roasts
                             #   ?scene=swiftplay    -> Swiftplay lobby demo
                             #   ?window=overlay     -> overlay demo
                             #   ?fullscreen         -> "League is set to Fullscreen" hint (combines with ?scene=)
                             #   ?profile=opgg       -> Profile page from OP.GG (client closed); ?profile=setup -> its Riot ID form
                             #   ?lp=N               -> Profile LP graph with N saved ranks (0/1 = division meter, >19 = longer climb)
npm run build                # Angular production build (check this compiles)
cd src-tauri; cargo test     # Rust unit tests (fixtures in src-tauri/tests/fixtures)
npm run tauri build          # local NSIS installer (needs the updater signing key in env; normally CI does this)
.\release                    # from main: bump, commit, push, start the release + website workflows (asks first; `.\release 0.2.0`)
                             #   same as ./release in Git Bash / zsh (the extensionless `release` sh script)
```

Before handing work back: `cargo test` and `npm run build` must pass with no warnings. For UI changes, check the browser demo, and update `src/app/core/demo.ts` when data shapes change.

## How it works

The Rust side runs one background loop (`engine.rs`, 1 s tick) that pushes state to the UI with Tauri events. The UI listens in `rift.service.ts`.

**Data sources (no Riot API key; game memory is never read):**

1. **League Client API (LCU):** local HTTPS on `127.0.0.1:<random port>` with basic auth `riot:<token>`. `lcu.rs` gets the port and token from the `LeagueClientUx` process command line, falling back to the `lockfile`. The certificate is self-signed, so the client accepts invalid certs for localhost only. Endpoints used:
   - `lol-gameflow/v1/gameflow-phase`, `lol-gameflow/v1/session` (queue/map, loading-screen teams)
   - `lol-champ-select/v1/session`, plus `PATCH lol-champ-select/v1/session/my-selection` for summoner spells
   - `lol-game-settings/v1/game-settings` → `General.WindowMode` (0 Fullscreen, 1 Windowed, 2 Borderless; same as `Config/game.cfg`, checked October 2026). Read on connect and every 15 s (`refresh_window_mode`) into `Status.window_mode`; the UI shows a "switch to Borderless" hint (`fullscreen-hint.ts`, Live tab + Settings → Overlay) while it's Fullscreen and the overlay is on.
   - `GET`/`PUT lol-item-sets/v1/item-sets/{summonerId}/sets` (shop build, `itemsets.rs`). `PUT` replaces the whole list, so read, swap our set, write back. Item `id`s are strings. Format checked with a real write and read-back in October 2026; block headers are kept ASCII because the in-game shop draws them.
   - `lol-perks/v1/pages`, `currentpage`, `recommended-pages/champion/{id}/position/{pos}/map/{map}`
   - `lol-lobby/v1/lobby/members/localMember/player-slots` (Swiftplay). Swiftplay (queue 480) has no champ select: you pick a champion, runes and spells per position slot in the lobby. In the `Lobby` phase the engine reads the slots every tick and imports each slot whose champion or position changed; the Live tab shows the slots (`swiftplay` event, `Shared.swiftplay`) with an "Import runes" button (`import_swiftplay_now`, every slot with a champion, even with auto-import off). `perks` is JSON in a string: `{"perkIds":[...],"perkStyle":8100,"perkSubStyle":8200}`. Runes and spells both go through `PUT player-slots` (the whole list, re-read first; skipped when nothing changed, since the client rejects a no-op PUT with "Put slots request matches current slots"); a live test (October 2026) showed a slot's new `perks` kept for 6 s+. **Never `PUT lol-perks/v1/currentpage` for Swiftplay:** the lobby links the current page to whichever slot is open in the client's champion picker (that once put Yasuo's runes on the Master Yi slot), and a newly made temporary page copies the current page's name. The rune menu shows, per slot, the page whose `quickPlayChampionIds` has the slot's champion (the slot's temporary page, or a page picked for it); those links can be empty (seen with the picker closed). After the slot PUT, the import gives that linked page the same runes and the League Bro name (`runes::set_linked_page`, only temporary or League Bro pages, never the player's own), and deletes leftover temporary pages named `League Bro:` that are deletable and linked to nothing (`drop_stale_temporary`). `lol-perks/v1/quick-play-selections/champion/{id}/position/{pos}` answers with the linked page's runes, not the slot's, so it isn't used as a check; the import re-reads `player-slots` after 500 ms and writes any slot that lost its runes once more. `POST player-slots/{index}/{perksString}` returns 400 INVALID_REQUEST, so it isn't used. Not yet confirmed: that the game starts on the slot's `perks`. Picks: the Live tab shows both slots side by side, each with its rec card (lookup mode); a pick there (or on the Champions tab for a champion + role in a slot) calls `choose_swiftplay_option`, kept in `Shared.swift_choices` until League Bro closes and used by every later import of that champion + position. All lobby writes return 400 while a game is running. Shop builds: one `League Bro:` item set per slot champion (`itemsets::apply_many`), written with the runes.
   - `lol-ranked/v1/ranked-stats/{puuid}`, `lol-match-history/v1/products/lol/{puuid}/matches` (scouting, and the Profile page via `profile.rs`). That endpoint returns only the requested player in each game, and the client keeps just a few dozen recent games (32 for Dom in October 2026, even when asked for 100). `profile::allowed` drops Brawl and League Classic games for both: League Classic by champion id ≥ 60000, Brawl by mode `BRAWL` / queue 2400 (not yet seen in real data, so check that when someone plays Brawl). The profile also drops custom/practice games, and its insights skip remakes. Lane/role in this data (`timeline.lane`/`role`) is unreliable, so there's no per-role breakdown. The profile's insights come for all queues plus per queue (`modes`). The page starts on All; the queue you're in (`current_queue_id`, from the gameflow session) gets a dot. For enemy and lane-opponent stats ("toughest" lists: 2+ games, more losses than wins), `profile.rs` also fetches each game's full record (`games/{gameId}`, 8 at a time, kept in memory for the session); the lane opponent is a guess (`positions`: Smite = jungle, `timeline.lane`/`role`, lower-CS bot laner = support) and is left empty when two players on either side land on the same position.
   - **LP gains/losses** (match history rows and the post-game hero, `rl-lp-change`): neither the client's match history nor OP.GG's MCP matches carry LP, so `lp_history.rs` works it out from League Bro's own saved rank points (`lp-history.json`, also the LP graph's data). Points are saved when champ select starts, after each game and on each Profile load; two points in a row whose wins + losses are one apart give the ranked game (420/440) that started between them `score(after) − score(before)` (100 per division, so a demotion to 75 LP shows as about −25). Games played while League Bro was closed get none, and so do two games between the same points (remakes don't count as games). After a ranked game the post-game summary shows at once and the engine re-reads ranked stats every 3 s (up to `POST_GAME_GIVE_UP`) until they count the game, then re-sends it with the LP. Not yet checked in a real ranked game.
   - `lol-match-history/v1/games/{gameId}` (post-game summary, `postgame.rs`). When a game ends (`in_game` → not), `end_game` clears the live state and the engine retries this every 3 s for up to 3 min, because the record shows up a few seconds after the game. Format checked against a real response in October 2026. `lol-end-of-game/v1/eog-stats-block` only exists on the post-game screen and its `stats` keys are untyped, so it isn't used. Each player gets a `position` from `profile::positions` (5v5 Summoner's Rift only). **Roasts** (`src/app/core/roast.ts`, "The Bro's review" card under the post-game hero, also in the profile's match detail): one red trash-talk line each for low CS/min, low kill participation (or KDA under 1), low damage share, lots of deaths and (supports) low vision, plus up to 3 green highlights (funny praise, not roasts; Dom, October 2026) for high CS/min, KDA or kill participation, damage share, few deaths and vision. Thresholds are by position (CS skipped for supports and when the position is unknown, ARAM gets its own death/KP bars); none for remakes or games under 10 minutes. Clicking any scoreboard row shows that player's review instead ("Back to you" or clicking them again returns). Lines are built from parts (`POOLS`): a lead that states the stat, a jab (the joke) and sometimes a sign-off tail, plus some whole lines, so each pool gives hundreds of lines. They're remembered in localStorage (`leaguebro.roasts`): a reopened game keeps its lines, and each pool skips its last ~75% of jabs so jokes don't repeat often. Settings → Post-game → Roasts (`showRoasts`) turns the card and the row clicks off. Lines stay free of swear words and never call the player "bro" (the app is the Bro) (Dom, October 2026).
   - `lol-game-data/assets/v1/{champion-summary,items,perks,perkstyles,summoner-spells}.json` (static data). `champion-summary` also lists League Classic copies of ~80 champions: same name, id = 60000 + the normal id, alias `Jade_…` (checked October 2026). `ChampInfo.classic` marks them (`is_league_classic`); the Champions tab lists them separately, and OP.GG lookups and the live-game name match skip them.
   - The schema reference is the swagger at https://github.com/dysolix/hasagi-types (`swagger.json`).
2. **Live Client Data API:** `https://127.0.0.1:2999/liveclientdata/allgamedata`, served while a game is running. `live.rs` uses it for objective timers, the next-item reminder, the skill-point hint and the lane item-value diff (`lane_diff`: you vs the enemy with the same `position`, summing `priceTotal` × `count` from the client's item list; none in ARAM etc. where positions are empty). It doesn't report enemy gold, so the diff is item value, like Blitz's; items are public on the scoreboard, so this is within Riot's rules. Its `scores.creepScore` only updates in steps of 10, so CS was removed from the overlay (Dom saw it not change in game); the game's own scoreboard shows the exact number. It also leaves out boots in the bot lane role-quest slot (checked October 2026), so the overlay remembers the last upgraded boots it saw you holding (`Engine::seen_boots`, reset each game); any upgraded boots count as the build's boots.
3. **OP.GG**, two sources with the same numbers, both unofficial for apps (they could change):
   - **Website API (tried first, ~0.3 s):** `lol-api-champion.op.gg/api/global/champions/{mode}/{championId}/{lane}` (the JSON behind op.gg's champion pages) plus `…/builds` in parallel, whose `single_items` depth 4–6 are the 4th–6th item options. `lane` is `top|jungle|mid|adc|support`, or `none` for ARAM/URF/Nexus Blitz. No `tier` param = Emerald+, which matches the MCP tool. Each list is every option, most played first, with no names; `web_to_mcp` takes the first of each into the MCP tool's `data` shape so `extract` reads both (plus the top `PICK_OPTIONS` (3) runes, spells, boots and core builds as `<key>_options`; the MCP fallback only has the top one), and the UI names runes and items from the client's data. Damage type comes from the League client's `lol-game-data/assets/v1/champions/{id}.json` (`tacticalInfo.damageType`, local and instant; that's why `recommend` takes the `Lcu`). Checked October 2026 to give the same runes, spells and damage type as MCP (`cargo test live_lookup_speed -- --ignored --nocapture` compares them and prints timings).
   - **MCP endpoint (fallback, ~3.5 s, most of it OP.GG's server):** `https://mcp-api.op.gg/mcp`, JSON-RPC over HTTP (MCP streamable HTTP), public, no key. Used only when the website API fails or takes over 5 s. `opgg.rs` does:
   - `initialize`, then `tools/call` → `lol_get_champion_analysis` with `game_mode`, `champion`, `position`, `lang`, `desired_output_fields`.
   - **The response is not JSON.** It's a compact text format: `class Name: field1,field2` header lines, then constructor-style values like `Runes(8112,[...],"Electrocute")`. `parse_compact` maps positional args to field names using the headers. Field order differs between classes (e.g. `SummonerSpells` has `win` before `play`), so always go through the headers.
   - Champion names: OP.GG accepts the client `alias` uppercased, in any format (`MONKEYKING`, `KAISA`).
   - `position` must be `top|jungle|mid|adc|support`. `all` and `none` are rejected for ranked **and** ARAM. ARAM and other modes take any lane value and ignore it, so the code sends `mid`.
   - `game_mode`: `ranked|flex|urf|aram|nexus_blitz`, picked from the queue/map (`game_mode_for`). Arena gets no recommendation.
   - Below `MIN_GAMES` (20) the data is noise (e.g. off-role picks). Runes and spells then fall back to the League client's recommended page.
   - Results are saved to disk (`%LOCALAPPDATA%\dev.dom.leaguebro\opgg`, one file per champion+position+mode) and expire on the patch cycle (`expires_at`): every 24 h for the week after a patch's notes come out, then every 7 days, and always when the next notes are due (`patch::notes_releases_around`, from `PATCH_SCHEDULE`). If OP.GG can't be reached, an expired answer is used only if it was fetched since the latest patch notes; otherwise runes fall back to the client. Bump `opgg::CACHE_FORMAT` when `Recommendation`, `extract`, `Matchup` or `parse_matchup` changes (saved matchups share it).
   - **Picking another option:** `Recommendation` carries `rune_options`, `spell_options`, `core_options`, `boots_options` (option 0 is always the top one; others need ≥ `MIN_GAMES`). The rec card shows them as chips when there's more than one. `RecChoice` holds the picked indexes and `opgg::with_choice` swaps them into the runes, spells, core, boots and `build_order` (`games` stays the top page's). In champ select the pick lives in `sh.rec.choice` (`choose_rec_option` → `engine::choose`, which re-imports runes, spells and the item set if you've picked that champion); `RecState::effective()` is what the overlay and imports use, and `for_ui()` is what the UI gets. A new champion/role starts back on option 0. The Champions tab only previews (`rec_with_choice`, nothing imported).
   - **Lane matchup (`matchup.rs`, `rl-matchup` card above the rec card):** in lane modes (`ranked`/`flex`), once you lock in (`engine::matchup_key`; hovering starts nothing, since each lookup is a ~3.5 s MCP call plus a match history read), then again whenever the enemy picks or the opponent pick change. The client doesn't say which lane an enemy plays, so the opponent is a guess: OP.GG's games per lane for each picked champion (`TierLists::lane_games`, from the tier list's one OP.GG request), every enemy put in a different lane, likeliest arrangement kept, and only if that champion plays your lane in ≥ 5% of its games (`guess_opponent`). The player can pick another enemy or none (`choose_lane_opponent` → `Shared::opponent_pick`, cleared each champ select). Only enemy champions are used, never names. `OpGg::matchup` fetches the website API with `?target_champion={id}` (same shape as the champion's own answer, matchup games only; checked October 2026) plus the MCP tool `lol_get_lane_matchup_guide` (JSON, ~3.5 s, the only source of `opponent_champion_tip`, `lane_advantage_champion`, `lane_solo_kill_advantage_champion` (a champion name or `EVEN`) and `recommended_play_style`); the guide also stands in when the website fails. The head-to-head record is the opponent's entry in the answer's `counters` (`win` = your champion's wins). Saved like recs (`rec-m-…` files) only when the tip came back. Your own record vs them is `profile::record_against` (match history lane opponents). The matchup lives on `RecState.matchup` (kept when `ensure_rec` republishes); `RecChoice.matchup` switches imports, spells, the shop set and the overlay to the matchup build (`RecState::effective`, only with ≥ `MIN_GAMES`), and a new opponent resets it to all games. `cargo test live_matchup -- --ignored --nocapture` checks it against OP.GG.
   - **Pick suggestions (`picks.rs`, `rl-pick-suggest` card at the very top of champ select):** only before you lock in, in lane modes with an assigned role, never Swiftplay (queues 480/490) (`picks::key`; `engine::champ_select` calls `picks::update` every tick, which only looks again when enemy/ally picks, bans or `Shared::opponent_pick` change, and sends `pick-suggestions` None on lock-in or when champ select ends). With a lane opponent (the player's `opponent_pick`, else `matchup::guess_opponent`) it reads the opponent's own OP.GG page in your lane (`{WEB_API}/{mode}/{opponent}/{pos}`, no query) and its `counters` (`win` = the opponent's wins, so yours = play − win), keeps champions in your lane's OP.GG tier list with ≥ 10 games, and ranks by the head-to-head mixed with 100 games of that champion's lane win rate. Without an opponent it's the tier list in OP.GG's order. Bans, every other picked champion and champions not in `/lol-champ-select/v1/pickable-champion-ids` are dropped; mastery comes from `/lol-champion-mastery/v1/local-player/champion-mastery` (both asked once per champ select). The card nudges picks that add the damage your team lacks (`damage.ts`) or answer the enemy comp (`comp.ts`: hand-made alias lists; 2+ tanks → "Shreds tanks", 2+ assassins/divers → "Stops dive", 2+ poke → "Engages on poke", 3+ picks with no tank → "Bursts squishies"), +1 win rate point per reason, at most 2, and shows 5 picks plus up to 3 of your champions (≥ 10k mastery). Its opponent buttons call `choose_lane_opponent`. Browser demo: `?scene=pick`.
   - **Situational items (`situational.rs`, `rl-situational` in the rec card, overlay "Situational" section):** `Recommendation.situational_pool` is every 4th–6th item option from the website's `/builds` (each item once, ≥ 10 games; the MCP fallback only has `later`'s three per slot). `situational::suggest` ranks those against a threat profile of the enemy team: healing, armor/MR stacking, shields, Health stacking, burst, heavy CC, and a lopsided AD/AP split. In champ select the profile comes from enemy picks (client roles, damage type, and the short `HEALERS`/`SHIELDERS`/`CC_HEAVY` lists); in game from each enemy's scoreboard items (stat amounts, lifesteal/shield items) weighted by KDA, recomputed every tick and emitted as `situational` when it changes. What an item answers comes from the client's item text (`item_tags` → `ItemInfo.situations`), not item ids. Owned items are skipped; a finished owned item fully answers non-stacking threats (anti-heal, penetration, anti-shield, cleanse) and takes one unit off stacking ones (Armor, MR, survive, %HP); a component you own marks its item "Started", and last tick's picks get a small bonus so the list doesn't flip on every purchase. With heavy healing and no anti-heal in the pool, a class-based fallback is added (`ANTI_HEAL_FALLBACK`, `offPool`). The overlay shows the top pick and a "+N more counters" toggle; it's a second clickable rect (`set_overlay_buttons` takes a list) so it works while the overlay is locked.
   - The Champions tab uses the `lookup_rec` command (any champion, `ranked` + role or `aram`). It returns the recommendation directly and doesn't touch `sh.rec`, which belongs to champ select. `RecCard` shows champ select's rec unless given a `lookup` input. Saved per-champion rune pages and builds were removed in October 2026 (old `runeOverrides` / `builds` keys in settings.json are ignored and dropped on the next save); rune auto-import switches are in Settings → Rune import.
   - The `scripts/opgg-probe*.mjs` scripts (if present locally) call the endpoint and save raw responses to `scripts/probe-output/` (git-ignored). Use them to see the real format; Claude's cloud sandbox couldn't reach op.gg.
   - **Profile without the client** (`opgg_profile.rs`): while League isn't running, the Profile page looks the player up on OP.GG by Riot ID + region (`Config.riot_id` / `region`, OP.GG codes like `na`, `euw`, `lan`). A real "log in with Riot" (Riot Sign On) needs a Riot-approved production app with a server, and asking for Riot passwords breaks Riot's terms, so it's Riot ID entry instead. The Riot ID and region are saved from the client (`/riotclient/region-locale`) the first time the Profile page loads with it running, or typed into the page's form. MCP tools `lol_get_summoner_profile` (name, icon from `profile_image_url`, level, `league_stats` ranks with divisions as numbers, `summoner_id`, `updated_at`, `renewable_at`) and `lol_list_summoner_matches` (limit 5–20, only the player's own line: no enemies, lane opponents, vision or trinket). Game ids are strings there, so `MatchLine.game_id` is the start time and the matches can't open a scoreboard. `game_type` maps to queue ids (`queue_id`); `NORMAL` covers draft, blind and Quickplay, so it's queue 0 labelled "Normal". OP.GG's data is only as fresh as its last update (seen 3 days old), so the page shows "updated … ago" and an **Update on OP.GG** button. The MCP tools have no update call and op.gg's website API (`lol-web-api.op.gg`) didn't answer from Dom's PC (`scripts/opgg-probe5.mjs`, October 2026), but looking up a stale profile makes OP.GG update it in the background (seen: `updated_at` jumped from 3 days old to the minute of the previous lookup, with the new level). So `renew` looks the player up and polls every 4 s, up to 45 s, until `updated_at` moves past what the page showed, or is under 2 minutes old (OP.GG's update cooldown, `renewable_at`). `MyProfile.source` is `client` or `opgg`; the page switches when the client opens or closes. OP.GG is never asked while the client is open: `get_my_profile`/`renew_profile` refuse while a `LeagueClientUx` process exists but hasn't connected yet (`lcu::client_running`), and the page shows "Waiting for the League client" and drops any load started against the old source. Fixtures: `opgg_mcp_summoner_profile.txt`, `opgg_mcp_summoner_matches.txt`.
4. **CommunityDragon** (`raw.communitydragon.org`) for champion, item, rune and spell icons (`assets.ts`). Client asset paths are lowercased and mapped there. While the League client is closed it's also the source of the static data (`StaticData`, from CommunityDragon's copy of the client's `lol-game-data/assets/v1` files at `util::CDRAGON_GAME_DATA`: `engine::load_statics_web`, loaded by the engine every minute until it works, and by the Profile page) and of the rec card's damage type, so the Champions and Profile pages work without the client. The client's own replaces it on connect.
5. **Riot patch notes** (`www.leagueoflegends.com`) for the Patch Notes tab (`patch.rs`). The site is Next.js, so `patch.rs` reads the JSON in `<script id="__NEXT_DATA__">`: the patch-notes tag page for the list, then each article's `richText.body` HTML, parsed with `scraper` into buffs, nerfs and adjustments. Only fetched when the Patch Notes tab is opened. Both are saved to disk (`%LOCALAPPDATA%\dev.dom.leaguebro\patch-notes`): a patch's notes are downloaded once and never again; the list is re-checked only when the next patch's notes are due (the day before that patch in `PATCH_SCHEDULE`, Riot's published dates; newest notes + 14 days once the table runs out), then at most every 6 h until they appear. **Add each new year's dates to `PATCH_SCHEDULE`** from https://support.riotgames.com/league-of-legends/gameplay/patch-schedule-league-of-legends. Bump `CACHE_FORMAT` when the parser or saved shapes change. `get_patch` only fetches URLs under `https://www.leagueoflegends.com/`. Fixtures: `tests/fixtures/patch_list.html`, `patch_article.html`.
6. **Champion guides** (`guide.rs`, the Champions tab's **Guide** view, `guide-card.ts`) for new players. The kit (difficulty 1–3, damage/attack type, the 0–3 `playstyleInfo` ratings, bio, passive + Q/W/E/R) comes from the client's `lol-game-data/assets/v1/champions/{id}.json` (CommunityDragon's copy while the client is closed). Each ability's `abilityVideoPath` (`champion-abilities/0103/ability_0103_Q1.webm`) is Riot's preview clip from leagueoflegends.com's champion pages, served at `https://d28xe8vt774jo5.cloudfront.net/` (allowed in the CSP as `media-src` and `img-src` for the `.jpg` poster; checked October 2026). Tips for playing as and against the champion are Riot's `allytips`/`enemytips` from Data Dragon (`ddragon.leagueoflegends.com/cdn/{latest}/data/en_US/champion/{alias}.json`); missing tips aren't an error. Kept in memory for the session. Longer video guides are a YouTube search opened in the browser (`open_guide_videos`, which builds the URL itself); there's no embed, since picking a video would need curation or a YouTube API key.

**Precedence rules (keep these):**

- Rune page: OP.GG (if ≥ `MIN_GAMES`), then the client's recommended page.
- Overlay build: OP.GG's `build_order` (if ≥ `MIN_GAMES` and `useRecommendedBuilds` is on). At game start the overlay shows OP.GG's starting items instead ("Start", `live::starter_items`, counts like "Health Potion ×2") until you own the ones that are kept (price ≥ 100, so potions and Control Wards don't count; with only consumables, until you own anything) or `STARTER_UNTIL` (2:30) passes; then the next-item section takes over. The overlay shows only the next item left of it (owned items drop off) with its remaining price, then that item's direct components still to buy in buying order: affordable now first (priciest first), then the rest cheapest first (`NextItem.components`, `live::components_left`, filled for the first item only; owned components drop off and partly built ones are priced after what you own inside them). Its top line holds the ability max order (the key to level next pulses), the lane item-gold diff ("VS", opponent's champion icon, a League-style coin stack, "+1.4k", `LaneDiff.champion_id`, which the engine fills via `Shared::live_champion`: the live API has no ids, so it matches `rawChampionName`'s suffix (the alias, same in every language) and falls back to the shown name; the scoreboard enemies for situational items use the same lookup; the top line has no hover text since the invisible drag layer covers it), the team item-gold diff ("Team", coin, "−1.3k", `live::team_diff`, every mode; both behind the `showLaneDiff` switch), and the padlock. Situational picks show their remaining price too (`live::price_situational`), and their reasons wrap; their tag ("SURVIVE BURST") is blue so it isn't mistaken for the red/green gold diffs. The overlay window resizes to the panel's height on every update (`fitOverlay`, needs `core:window:allow-set-size`); 460 px in `tauri.conf.json` is only the starting height; the width comes from Settings → Overlay → Width (`overlayWidth`, default 340 CSS px so the header fits on one line, 260–480), and Size (`overlayScale`, 80–150%) is a CSS `zoom` on the overlay host. The host is laid out at `width / scale` so its measured size is right before the window is resized (`fitOverlay(width, height)`); the header wraps if it doesn't fit.
- Shop item set: on lock-in (same rules as spells: OP.GG, ≥ `MIN_GAMES`, `setItemSets` on), one set titled `League Bro: <Champ> <Role>` for that champion and map, blocks Starter / Build order / Core build (the picked one, then every other core option the rec card offers) / Boots (all offered, picked first) / 4th-6th item options. Any other `League Bro:` set is replaced (Swiftplay writes one per lobby slot instead); the user's own sets are never touched. **Where it goes:** the shop lists sets that apply to every champion first and opens on the first one, and the client rewrites the `sortrank` apps send (champion sets always become 9999, checked October 2026), so a set in the client's list can't get ahead of a player's own global set. So, like Blitz, League Bro writes its sets as files, `Config\Global\Recommended\!!!!league-bro-<n>.json` (four `!` sorts ahead of Blitz's `!!!blitz-`), and removes any `League Bro:` set from the client's list. The client-list write is only the fallback when the install folder isn't found. Global files show for every champion and outlive the app, so they're removed when champ select starts, when League Bro quits (main window close), and on its first phase after connecting outside a game. They're not removed at game end, because Swiftplay writes them in the lobby and only rewrites when a pick changes. Each file also carries `associatedChampions`; whether the game honors that for global files is untested.
- Other apps' global item sets: the game reads item sets from files under `<install>\Config`; the client writes its own list there as `RIOT_ItemSet_<n>.json`, and some apps (Blitz: `Global\Recommended\!!!blitz-<n>.json`, seen October 2026) write files straight into `Config\Global\Recommended`. Global sets show for every champion, stay after the app closes, and are listed before champion-specific ones, so they can push League Bro's set out of the shop's dropdown. Settings → Recommendations lists them (`itemsets::scan_global`) and moves them to `Config\Global\Recommended-moved-by-league-bro` on request, with a put-back button. Never automatic, and never the client's own `RIOT_ItemSet_*` files. The install folder comes from `GET /data-store/v1/install-dir`, else Settings.
- Summoner spells: `arrange_spells` keeps each recommended spell in the slot where the player already has it, so Flash stays on their usual key.
- Overlay mouse handling: the overlay is always locked = click-through, except over its buttons (the round move handle on its top-right corner, the lane gold diff's enemy picker and the situational "more counters" toggle). `watch_overlay_cursor` (engine.rs, 50 ms) hit-tests the cursor against the button rects the overlay reports (`set_overlay_buttons`, a list, CSS px; re-measured on every overlay update since rows above the toggle move it) and toggles `set_ignore_cursor_events`. There is no unlocked mode any more (Dom, October 2026: hold the handle, drag, let go). Dragging is League Bro's own (`drag_overlay` with `step` start/move/end: pointer capture on the handle, the window follows the cursor's physical position, `end` saves the spot; the watcher keeps the window clickable while a drag is on), **not** `data-tauri-drag-region` or `startDragging`: Windows' move loop calls `ClipCursor(NULL)` when a drag ends, which freed the cursor from League's window so it slid onto a second monitor until alt-tab (seen with two monitors, October 2026). The overlay window is `"focusable": false` in `tauri.conf.json` (tao sets `WS_EX_NOACTIVATE`), so clicking it (the handle, "more counters", dragging) doesn't take focus from League; before that, the next click in the game only gave League its focus back (Dom noticed, October 2026). Hiding the overlay also saves its position (`save_overlay_position`).
- Overlay contents: Settings → Overlay → "Show on the overlay" has one switch per part. `showLaneDiff` and `showTimers` only hide those parts in the overlay window (`overlay.ts`), so the Live tab keeps them; `showSkillHint` and `useRecommendedBuilds` are applied in the engine and need OP.GG recommendations (greyed out in Settings otherwise). The move handle always shows.
- League Bro owns exactly one rune page, named `League Bro: <Champ> <Role>` and kept to 25 characters or fewer (`page_name`). It overwrites that page in place each time (PUT, so it needs no free slot), and deletes any extra `League Bro:`, `Riftlight:` or `LB:` pages (`is_ours` matches the prefix plus `:`). With no page of its own and every slot used (POST answers 400 "Max pages reached"), it takes over the selected editable page (else the one edited longest ago) and says which in the import message; from then on that page is League Bro's. "Keep my pages when slots are full" (`keep_my_pages_when_full`, off by default) makes it fail instead. Swiftplay's temporary pages never count as League Bro's page.

## Riot rules (hard constraints)

These keep users safe from bans. Don't add features that break them, even if asked; explain why instead.

- Never read or write game memory, inject into the game, or automate input (no auto-accept, no scripts). The overlay is a separate always-on-top, click-through window, not something drawn inside the game.
- **No overlay in League's Fullscreen mode.** Tested October 2026: League's Fullscreen covers the always-on-top overlay window, even with topmost reasserted every tick. Apps that show overlays there (e.g. Blitz, a Riot-approved app) most likely draw inside the game's rendering, which means injecting into the game. That's off-limits here, and Vanguard would likely flag it for an unregistered app. Tell users to use Borderless or Windowed (the app does, via the Fullscreen hint). Riot Developer Portal registration doesn't grant in-game drawing. An Xbox Game Bar widget does show over League's Fullscreen (Dom tested a pinned Game Bar widget, October 2026) and isn't injection, but it's a separate packaged UWP app with its own install and certificate, so Dom decided against it.
- **No enemy cooldown tracking**: no ultimate timers (banned March 2025) and no summoner spell timers. Objective timers are fine (dragon, Baron, inhibitors).
- In **ranked champ select**, don't reveal hidden teammate or enemy names or stats (`nameVisibilityType: HIDDEN`). Everyone is shown from the loading screen on, except players using streamer mode.
- No Brawl or League Classic match data.
- The app isn't registered with Riot. Fine for personal use and a few friends; public distribution would need Riot's developer portal approval.

Sources: Riot dev policies (https://developer.riotgames.com/policies/general), Overwolf's LoL compliance page, Riot's 12.22 champ select post.

## Feedback

The Feedback tab (`feedback-view.ts`) is written for players, not developers: "Something's not working" / "I have an idea", a "Where did it happen?" chip (pre-picked from the gameflow phase), one required text box, an optional follow-up, an optional "Want a reply?" contact, and an "Include app details" switch (League Bro version, OS version, client phase; added in Rust by `feedback.rs`). No GitHub account is needed. Every report becomes a public GitHub issue, and the page says so; the contact field stays private (October 2026). The app never talks to GitHub itself: a token shipped in the app could be pulled out of the installer.

`send_feedback` posts to the Worker in `feedback-worker/` (`leaguebro-feedback`, deployed October 2026 on Daniel's (dgriego's) Cloudflare account at https://leaguebro-feedback.eggomygriego.workers.dev, so only he can redeploy it; moving it changes the URL and needs an app release; URL in `feedback::URL`, `LEAGUEBRO_FEEDBACK_URL` at build time overrides it). The Worker:
- `POST /api/report`: stores the report in D1 (`reports` table, made by the Worker on first use), answers the app, then (`waitUntil`) opens an issue in doliaro/leaguebro labelled `bug` or `enhancement` plus `from-app`, with the `GITHUB_TOKEN` secret, and saves its link. No auth; 10 reports per IP per hour (an IP's SHA-256 hash is kept only for that hour, then wiped, since an IPv4 hash can be reversed); fields are trimmed to fixed lengths. At most `AUTO_ISSUES_PER_DAY` (30) automatic issues per UTC day; past that, or when GitHub fails, the report has no issue and the inbox offers to make it. Making an issue first claims the report (`github_url` = `pending:<time>`, one UPDATE that also checks the cap), so the automatic run and the inbox button can't both file it; a claim older than 2 minutes counts as abandoned. Players' text goes in as a Markdown quote with a zero-width space after `@` and `#`, so it pings nobody, links no other issue and can't pass for the issue's own sections; the contact field never goes into the issue. Reports stay "new" until a dev marks them done, so ones asking for a reply aren't missed.
- `/` is the devs' inbox page (New / Done / All, bugs/ideas filter), behind the `ADMIN_PASSWORD` secret: contact info, spam deletion, and a **Create GitHub issue** button for reports that have no issue yet. Report text is put on the page with `textContent` only, since it comes from the public.

Working on it: `cd feedback-worker; npm install`, then `npm run dev` (Vite + workerd on http://localhost:8799, local D1; put `ADMIN_PASSWORD=...` and a dummy `GITHUB_TOKEN=...` in `.dev.vars`, git-ignored). To check issue creation without touching GitHub, start it as `GITHUB_API=http://localhost:8798 npm run dev` with a fake server there (the `GITHUB_API` binding is read from the environment by `cloudflare.config.ts`; `.dev.vars` doesn't override it). Check types with `npx tsc -p .`. Deploy with `cf deploy`; set secrets with `npx wrangler secret put ADMIN_PASSWORD --name leaguebro-feedback` (and `GITHUB_TOKEN`), since `cf` can't set a single secret yet. `cargo test live_feedback -- --ignored` with `LEAGUEBRO_FEEDBACK_URL=http://localhost:8799/api/report` sends a test report from Rust.

## Releases and auto-updates

- Version lives in `src-tauri/tauri.conf.json`, `package.json` and `src-tauri/Cargo.toml`, mirrored in `package-lock.json` (twice) and `Cargo.lock` (the `leaguebro` entry). Bump with `bump` from the project folder (next patch version, one above the current version or newest local `v*` tag) or `bump <x.y.z>`; `bump.cmd` just calls `scripts\bump-version.cmd`. It edits just those six spots (no find-and-replace; the lock files hold unrelated packages at the same version numbers), refuses a version not higher than the current one or the newest local `v*` tag, and writes nothing unless every spot matched.
- Dom pushes, then runs **Actions → Release installers → Run workflow**. Or `release` (`release.cmd` → `scripts\release.ps1`) does it all from `main`: checks it's clean and not behind GitHub, fetches tags, bumps, asks, commits `bump to x.y.z`, pushes, and starts `build-windows.yml` and `pages.yml` with `gh` (tauri-action makes the tag and release). Answering no puts the version files back. The workflow publishes `League.Bro_x.y.z_x64-setup.exe`, `League.Bro_x.y.z_universal.dmg`, the updater bundles with their `.sig`s, and `latest.json`.
- Installed copies check `releases/latest/download/latest.json` on startup and every 6 h, then show an "Update and restart" banner. Dev builds never self-update (`isDevMode()`).
- Updates are signed. The private key and password are the repo secrets `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the public key is in `tauri.conf.json`. Never change the pubkey unless Dom has lost the key, because that breaks updates for everyone already installed.
- The website (`site/`) needs no change per release. Keep its copy in step with the app when features change, and keep the Riot "isn't endorsed by Riot Games" notice in its footer (required for fan projects). It uses no Riot logos or champion art.
- The installs are unsigned for Windows (SmartScreen "Run anyway"). Code signing (e.g. Azure Trusted Signing) is a possible future step.
